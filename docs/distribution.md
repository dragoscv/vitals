# Distribution and code signing

How Vitals is built, signed and delivered — and, honestly, what the free
approach does not solve.

## The problem

Windows shows **SmartScreen** on any executable it has not seen before:

> Windows protected your PC
> Microsoft Defender SmartScreen prevented an unrecognised app from starting.

Running it requires clicking _More info_ → _Run anyway_. Most people close the
dialog instead. (Vitals does not install a service — the privileged helper
is not shipped, ADR 0012 — so the only thing Windows is judging is the
installer itself.)

## What actually removes the warning, and what it costs

| Approach                | Cost/year | Removes SmartScreen                             |
| ----------------------- | --------- | ----------------------------------------------- |
| Unsigned                | Free      | No                                              |
| Self-signed certificate | Free      | **No** — worse, it looks like forgery           |
| Sigstore / cosign       | Free      | No (not a Windows trust root)                   |
| Certum Open Source (OV) | ~€30–60   | Only after building reputation, weeks to months |
| OV / EV certificate     | ~€250–600 | Reputation-based for both since 2024            |
| SignPath Foundation     | Free      | Reputation-based; needs an established project  |
| Microsoft Store         | Free\*    | Yes — Store installs never show SmartScreen     |

\* Individual developer registration has been free since September 2025.
Azure Artifact Signing (formerly Trusted Signing) is not offered to individual
developers outside the US and Canada, so it is not an option for this project.

There is no path — free or paid — to an immediate SmartScreen bypass through
direct download any more: since 2024 EV certificates build reputation the same
way OV ones do. The Store is the only warning-free route.

## What we do

### 1. Reproducible builds, publicly verifiable

Every release is built by a GitHub Actions workflow from a tagged commit. The
workflow file is in the repository, so anyone can read exactly what produced
the binary. This does not stop SmartScreen but it does mean nobody has to
trust a binary blob built on a developer's laptop.

### 2. Checksums and build provenance

Every artefact ships with a SHA-256 checksum and a
[SLSA provenance attestation](https://slsa.dev), generated by
`actions/attest-build-provenance`. This is free, and it cryptographically
links a binary to the exact commit, workflow and runner that produced it.

Verify a download:

```powershell
# Checksum
Get-FileHash .\Vitals_x64-setup.exe -Algorithm SHA256

# Provenance, with the GitHub CLI
gh attestation verify .\Vitals_x64-setup.exe --repo dragoscv/vitals
```

Stronger than a code-signing certificate in one specific way: a certificate
proves _who_ built it, provenance proves _what source_ built it. It is weaker
in the way that matters commercially — Windows does not check it.

### 3. Microsoft Store, as an MSIX that Microsoft signs

The Store is the only route to a warning-free install. Registration is free
for individuals. Vitals takes the **MSIX route**: the package is uploaded
unsigned and Microsoft signs it, so no code-signing certificate is needed.
Tauri has no MSIX bundler, so `packaging/msix/build-msix.ps1` lays the
package out from the release executables and the generated brand assets.

The Store build is the **same binary**; Store policy is applied at run time
(`apps/desktop/src-tauri/src/distribution.rs`) when the process has package
identity:

- **no self-update** — the Store updates the package;
- **no Task Manager replacement** — its HKLM IFEO write is virtualised;
- **no sensors service or driver** — not shipped in the package; CPU
  temperature falls back to what Windows reports without it;
- **start with Windows** and the watchdog use the manifest's
  `windows.startupTask` entries, because Run-key writes are virtualised too.

Trade-offs, stated plainly:

- **Certification review** adds days to each release, so the Store lags the
  direct download.
- **The listing must never change underneath Microsoft.** For the EXE route
  the URL they review has to keep serving the same bytes, so the Store points
  at a versioned asset, never at `latest`.

### 4. Honest documentation of the warning

The download page and README explain the warning, show the expected checksum,
and tell people how to verify it. Pretending it does not exist trains users to
click through security warnings — the same failure the process-termination
risk model exists to avoid.

## If signing is funded later

The switch is small and localised:

1. Add `WINDOWS_CERTIFICATE` (base64 PFX) and
   `WINDOWS_CERTIFICATE_PASSWORD` repository secrets.
2. That is all. `release.yml` imports the certificate and passes the
   thumbprint to `tauri build` through a `--config` override; with the secrets
   absent it builds unsigned and says so.

Deliberately not designed around: nothing in the build depends on signing
being absent.

## Update signing is separate, and is already done

Tauri's updater verifies a **minisign** signature on every update package
before applying it. That key is ours, costs nothing, and is unrelated to
Windows code signing.

This matters more than SmartScreen for ongoing safety: it means a
man-in-the-middle cannot serve a malicious update, even though the initial
download shows a warning. The private key lives only in repository secrets
and on the maintainer's machine under `%USERPROFILE%\.tauri`, never in the
repository (`docs/releasing.md`).

## The command line (`vitals`)

The CLI is distributed as a plain zip, not an installer:
`vitals-cli_<version>_<arch>.zip`. `release.yml` builds it in the `Build CLI`
step and attaches it to the same GitHub release as the desktop installers. It
contains `vitals.exe`, `LICENSE` and `THIRD_PARTY_NOTICES.md`.

It is deliberately **not inside the NSIS installer**: the installer and the
Scoop package are the desktop app only, so a headless server or a CI runner can
have the CLI without a GUI install. The Scoop manifest names the zip as a
separate download rather than unpacking a second archive into a package built
around the installer. `docs/cli.md` documents install, every subcommand and the
exit-code table.

### A Windows binary that ships needs a `build.rs`

`rustc` writes no resource section of its own. A Windows process takes its icon,
its product name, its file version and its publisher from that section, so a
binary compiled without one is drawn with the generic application icon and its
"Properties → Details" is empty — in Explorer, in Task Manager, and in the
Defender Firewall prompt a server raises the first time it binds a port. 1.5.0
shipped exactly that: `vitals.exe` in the CLI zip, and the watchdog and sensor
binaries inside the installer, all with no icon and no version at all, while
`vitals-desktop.exe` was fine — because Tauri runs a resource compiler for that
binary (`tauri-build`, from `bundle.icon`, `productName`, `publisher` and
`copyright` in `apps/desktop/src-tauri/tauri.conf.json`).

So every crate with an executable that reaches a user carries a `build.rs` that
embeds the resource — `apps/cli`, `apps/watchdog` and `crates/vitals-sensors`
today, all three with the same code, and `tauri-winres` as a build dependency
(already in the tree through `tauri-build`, so no new crate and no new licence).
The icon is the file the desktop app uses, so one mark is regenerated in one
place; the strings are held to `tauri.conf.json` rather than written twice.

Two gates hold this, at the two ends where it can break:

- `scripts/check-drift.ps1` fails if the three `build.rs` files stop naming the
  icon, the product, the publisher or the copyright — a source-side check, so it
  runs on every commit, in `verify.ps1`.
- `scripts/check-binary-identity.ps1` reads the identity back **off the built
  artefacts**: the installer and the CLI zip in both Windows legs of
  `release.yml` (against the desktop binary as the icon reference), the
  published assets again in the `readback` job after the release, and both MSIX
  packages in `packaging/msix/build-and-upload.ps1`. A source test cannot catch
  this class of defect — the source was correct-looking all along; only the
  bytes can say what a user will see.

  It also runs in the `checks` lane of `scripts/verify.ps1`, against the same
  binaries a local `tauri build` leaves under `target/release`
  (`vitals-desktop.exe` as the icon reference, so the CLI, the watchdog and the
  sensors helper are compared to the mark the desktop carries). There it reads
  only what is already there: nothing is built and no network is touched, and
  when no binary is present — or the only ones are older than the last change to
  the version sources, so they report a version the tree no longer declares — it
  prints one `binary identity: skipped` line and exits 0, so the table never
  depends on a build. CI's release job checks the whole published set regardless.

  The last two call sites pass `-SkipIcon`: a Store package carries an x64 and
  an ARM64 binary and one host cannot draw both marks, and the readback job's
  reference is not itself a published file. That switch drops the **reference**
  together with the comparison — a caller that has said it cannot compare must
  not be failed for not supplying the binary it would have compared against —
  and the verdict line names what was and was not proved, so "the mark, the
  product, the publisher and version X" and "the product, the publisher and
  version X" cannot be read as the same result.

For the same reason `apps/helper` is **not shipped**: its service host is still
a stub that exits at startup, and nothing packages `vitals-helper.exe`. It stays
in the tree as the place the elevated helper will live, and the gates above are
what will hold it to the same identity when it does ship.

## Samsung TVs (Tizen): sideload only

The Tizen app (`apps/tizen`) is a web app packaged as a **`.wgt`**, and it is
distributed by sideload only. There is no store route: Samsung Seller Office
review needs a store-signed package and a registered seller account, and the
app's only network use is the LAN pairing described in its own README.

What "sideload only" means in practice:

- **The package is signed with a distributor certificate that names one
  device.** The `mixai-samsung` profile's certificate carries a single DUID
  (the owner's Odyssey G8), so a `.wgt` built from it installs on that TV and
  no other. Handing the app to a second person means a new certificate, which
  is a Samsung-side process, not a code change.
- **The TV must be in developer mode**, with the building PC's IP set as its
  developer host, and Tizen Studio (`sdb`) installed on that PC. None of this
  is something an end user could be asked to do.
- Because of the two points above, the Tizen app is **not a downloadable
  artefact in a release**: `release.yml` does not carry it and the download
  page does not offer it. It is built and installed by hand, on the owner's
  machine.

### Build and package — the release lane

The release-time entry point is one script, `scripts/tizen-package.ps1`. It
builds the bundle, signs it, checks the result is genuinely signed, and writes
a versioned `.wgt`:

```powershell
pwsh -NoProfile -File scripts/tizen-package.ps1            # build, sign, verify, publish
pwsh -NoProfile -File scripts/tizen-package.ps1 -DryRun    # print the plan, build nothing
pwsh -NoProfile -File scripts/tizen-package.ps1 -SkipBuild # sign an existing apps/tizen/dist
```

- **Prerequisites**, every one checked before anything is built, and every one
  fatal:
  - **Tizen Studio** at `%USERPROFILE%\tizen-studio` (or `$env:TIZEN_STUDIO`,
    or `-TizenHome <path>`), providing `tools\ide\bin\tizen.bat`. `sdb.exe` is
    reported but **not** required: it is only used to install, and packaging
    never talks to a device.
  - **A Samsung certificate profile** — `mixai-samsung` by default
    (`-CertProfile`), listed in
    `%USERPROFILE%\tizen-studio-data\profile\profiles.xml` (or
    `$env:TIZEN_STUDIO_DATA` / `-DataHome`). It is created once in Tizen
    Studio's Certificate Manager; its keystore and its password live beside it
    and are secrets, never committed and never passed on a command line.
  - The **version**, read from `scripts/version.ps1` and cross-checked against
    `apps/tizen/public/config.xml`. A disagreement stops the run rather than
    shipping a package that kept last release's number.
- **What it produces**: `apps/tizen/build/Vitals_<version>.wgt` — a directory
  `.gitignore` already covers — with a `SHA256SUMS.txt` beside it. The script
  prints the size, the SHA-256 and the signature entries it found.
- **`-DryRun`** prints the exact command sequence and the state of every
  prerequisite, builds and writes nothing, and **exits 0 even on a machine
  without Tizen Studio** — which is how the lane's logic is proved without the
  SDK.
- **Exit codes**: `0` packaged (or a dry run); `1` a prerequisite is missing;
  `2` the bundle build failed; `3` the Tizen CLI could not package; `4` the
  package is not a signed `.wgt`; `5` the version surfaces disagree.

Signing is not a separate step, so there is deliberately no `-Sign` switch:
`tizen package -t wgt -s <profile>` signs in the same command that assembles
the archive, and a "package only" mode beside a "package and sign" mode would
be one mode with two names.

The app's own scripts stay for development:

```powershell
pnpm --filter @vitals/tizen build          # tsc + vite → apps/tizen/dist
pnpm --filter @vitals/tizen build:wgt      # that build, then package via tv-deploy.ps1 -NoInstall
pwsh -NoProfile -File apps/tizen/scripts/tv-deploy.ps1 -NoInstall # package only, no device
```

Both `tv-deploy.ps1` and `scripts/tizen-package.ps1` stage from a TEMP copy of
`dist`, never packaging inside it, because `tizen package` signs in place and
would leave its author/signature XML inside the bundle. The release script then
asserts the signature is actually there, which is the one thing a TV refuses.

CI (`.github/workflows/ci.yml`, job `tizen`) builds the bundle and a `.wgt` on
every change to `apps/tizen` — before this job the TV app was never compiled in
CI at all — and uploads both in the `vitals-tizen` artifact. Where Tizen Studio
and the certificate profile are present (a self-hosted runner or the
maintainer's machine) it builds the **signed** `Vitals.wgt` via
`tv-deploy.ps1 -NoInstall`, which never opens a device connection and so needs
no TV present. Where they are not — a hosted runner has neither — it assembles
the same archive **unsigned**, as `Vitals-unsigned.wgt`: the layout and the
bundle are checked, but a TV will not install it, because the signature is
exactly what `tizen package` adds. The release lane is this same packaging
step with the prerequisites and the signature asserted rather than assumed.

### Install on a TV or Smart Monitor

The `.wgt` is installed over the network by `sdb`, which is why the device has
to be prepared first:

1. On the TV: open **Apps**, press `12345` on the remote to open the developer
   menu, turn **Developer mode** on, set **Host PC IP** to the address of the
   machine that will build the app, and reboot the TV so it takes effect.
2. On the PC, with the TV on the same network:
   `sdb connect <tv-ip>:26101`.
3. Install and launch it:

   ```powershell
   pwsh -NoProfile -File apps/tizen/scripts/tv-deploy.ps1            # package, install, launch
   pwsh -NoProfile -File apps/tizen/scripts/tv-deploy.ps1 -DevTools  # launch in debug, DevTools on :9222
   ```

   `tv-deploy.ps1` connects to the device (default `192.168.100.135:26101`,
   `-Device`), kills a running instance, installs and runs it.
   `scripts/tizen-package.ps1` is the release _packaging_ half and never opens
   a device connection, so it can run where no TV is present.

### Signing and certificates

- The signature is a **distributor certificate** made once in Tizen Studio's
  Certificate Manager and stored as a profile (`mixai-samsung`), with an author
  certificate and a keystore beside it. `tizen package -s <profile>` needs no
  separate key step and no device.
- That certificate **names one device's DUID**, so a `.wgt` signed with it
  installs on that device and no other. A second TV means a new certificate — a
  Samsung-side process, not a code change — and a public release would need
  Samsung Seller Office and a store-signed package, which this app does not do.
- Because signing needs only the profile files and not the device, the package
  can be built on any machine that holds the profile. CI relies on exactly
  that.

### Failure modes

| What you see                                             | Cause                                                                        | What to do                                                                                                                                                                                        |
| -------------------------------------------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Exit **1**, naming `tizen.bat`                           | Tizen Studio is not installed, or not where the script looks                 | Install it under `%USERPROFILE%\tizen-studio`, set `$env:TIZEN_STUDIO`, or pass `-TizenHome <path>`                                                                                               |
| Exit **1**, naming the profile                           | No `profiles.xml`, or the profile name is absent from it                     | Create the profile once in Tizen Studio's Certificate Manager, or pass `-CertProfile`                                                                                                             |
| Exit **4**, "not signed"                                 | A package was produced with no signature — the hosted-runner fallback output | Check the profile is usable; an unsigned `.wgt` a TV refuses to install                                                                                                                           |
| Exit **3** from the Tizen CLI                            | The profile's certificate is unusable or the keystore password is wrong      | Re-create the profile; never put the password on a command line                                                                                                                                   |
| The TV refuses the install, or the app will not start    | The bundle's `required_version` is higher than the device's Tizen version    | `required_version` is 7.0 and the bundle targets Chromium 94, so it runs from Tizen 7.0 up; a device below that needs a lower floor in `apps/tizen/public/config.xml` and a matching build target |
| The install fails with an unknown- or wrong-device error | The certificate's DUID is not this device's                                  | Rebuild with a certificate whose DUID matches the device                                                                                                                                          |

The bundle targets Chromium 94 and `required_version` is 7.0 (Tizen 7.0), so
one `.wgt` covers every supported TV up to and including the Odyssey G8's
Tizen 9. See `apps/tizen/README.md` for the app itself.

## Summary

- SmartScreen on first run is **expected** for the direct download. Documented,
  not hidden.
- Provenance and checksums give verifiability without a certificate.
- The Store listing ships as an MSIX signed by Microsoft (`packaging/msix/`).
- Updates are cryptographically verified regardless of channel.
