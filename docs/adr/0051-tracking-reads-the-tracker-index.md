# 0051 — Tracking draws agentq's tracker index, read-only

- **Status:** Accepted (2026-11-28)
- **Slice:** S26-32
- **Supersedes:** none

## Context

Every repository on this machine keeps its own plan or tracker — `docs/tracker.csv`
plus its narrative here, a `PLAN.md`/`CSV` pair elsewhere — and each has its own
columns and its own status words. The owner asked to see them together in Vitals:
what is in progress, what is blocked, which repositories have drifted from the
conventions, without opening eight windows to find out.

There is already a tool for this, and it is not ours: `agentq`'s
`tools/tracker-lint.mjs`. Each repository declares how its tracker is read in
`.agentq/trackers.json`; the tool maps the columns and the status words onto one
canonical vocabulary (`todo`, `in-progress`, `blocked`, `review`, `done`,
`dropped`, `deferred`), reports the shape defects that have actually happened
(arity, duplicate ids, an unmapped status, a narrative id that points at
nothing), and in `--scan` mode writes **one** merged index to
`%USERPROFILE%\.codai\coord\trackers\index.json`. Its own header names this page
as a consumer.

Three routes were available: read that index; call the tool from the app and
parse its stdout; or give Vitals its own reader for every tracker file format
and location.

## Decision

Vitals reads the index file the tool writes, and reads only that.

1. One Rust command, `get_tracker_index`, resolves the coordination directory
   through `vitals_agents::agentq::default_root()` — the same function the AI
   page's readers use, so `AGENTQ_HOME`, `USERPROFILE` and `HOME` are honoured
   in exactly one place — and returns the file's contents verbatim. It is
   `async` (`spawn_blocking`) because it touches the disk, and it returns
   `null`, not an error, when the file is absent: a machine that has never
   scanned has no index, which is a normal state with its own screen.
2. **No wire type.** The index is an external artefact owned by another tool, so
   it is not in the protocol crate: the frontend parses it tolerantly
   (`features/tracking/model.ts`) and validates rather than trusts, exactly as
   `ProjectsPanel` parses its own answer. A ts-rs binding would pretend Vitals
   owns a shape it does not, and would have to be regenerated by whichever
   change lands in the other repository first.
3. Every field is optional and every figure that cannot be computed is absent
   rather than zero — the repository AGENTS.md rule applied to someone else's
   document. An unmapped status keeps the raw token the scanner recorded instead
   of being dropped, because a row that exists in a tracker must not vanish from
   the view of it.
4. **Read-only, and it cannot be otherwise.** No command writes, the page offers
   no action on a row, and no state is cached on disk. The index is a rebuildable
   view; the per-repository tracker is the record, and Vitals is not a second
   writer of it.
5. One read per visit, plus a manual Reload: the index changes when a person runs
   a scan, which is an act and not a stream. Visibility gating follows the other
   pages (`useAgents`, `useProjects`), so a launch in a tray does not read.

## Consequences

- The page works with `agentq` stopped, with the daemon never started, and on a
  repository that has never been scanned: the index is a file, and the absent
  case has its own empty state naming the command that fills it.
- Vitals cannot corrupt a tracker, and cannot disagree with the linter about what
  a tracker says: both read the same canonical mapping, and the page draws the
  findings the linter wrote rather than re-deriving them.
- The scan is a snapshot, not live data. The page says which scan it is drawing
  and how long ago it ran, so a stale catalogue is visible as one instead of
  being mistaken for the current state.
- What the page cannot say without the Codwen account is whether projects are
  healthy — that is the Codwen projects contract, a different slice. All this
  page claims from a stored account is locality: local-only, or connected.
- Rejected: spawning `tracker-lint.mjs` from the app (a Node process and a
  JavaScript toolchain as a runtime dependency of a Rust monitor, for data a file
  already holds); reading every tracker format directly (two parsers for one
  vocabulary, and the linter exists for exactly that reason); an event watcher on
  the index (more moving parts than one read per visit); and marking or editing a
  row from the window (ADR-0009 — the CSV is state, the narrative is reasoning,
  and the agent that owns the repository writes both).
